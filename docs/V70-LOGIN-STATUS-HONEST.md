# v70 login (ошибка 10101) — честный статус реверса

Этот документ фиксирует **проверенные** факты и **честно** — что ещё не сделано.
Он важнее бодрых формулировок в истории коммитов: предыдущий коммит
(«Шифр логина вскрыт эмулятором») **преувеличил** — байт-точный шифр логина
НЕ восстановлен. Ниже — реальное положение дел.

## Что доказано (ground truth из pcap + эмулятора libg64.so)

1. **Порядок кадров.** В успешном коннекте настоящий клиент шлёт
   `ClientHello(10100)` → `Login(10101)` → пачку игровых сообщений (10110, …)
   **одним залпом, ДО прихода `ServerHello(20100)`**. Значит бокс логина
   **не зависит** от `ServerHello` и его 24-байтного session-значения. Это
   противоречит нашему клиенту, который ждёт `ServerHello` и только потом шлёт
   логин (`Messaging/Messages/Server/ServerHelloMessage.js:8`).

2. **Структура логина (из `login_0027.bin`, 332 Б payload):**
   `cpk(32) || MAC(16) || ct(284)`. Тело логина (plaintext) = 284 байта.
   `ServerHello` = `len(24) || server_nonce(24) || 0xffffffff`.

3. **Модель крипты клиента в `Crypto/ModernCrypto.js` структурно ВЕРНА:**
   - конверт `cpk || box` ✓
   - nonce = `blake2b24(cpk, serverPublicKey)` ✓
   - ключ = `DH(csk, serverPublicKey)` (асимметричный бокс первого сообщения) ✓
   - в plaintext вшит клиентский session-nonce ✓
   **Единственное, что неверно — само ядро шифра** (`primitives.box` =
   стандартный tweetnacl xsalsa20poly1305).

4. **DH — это СТАНДАРТНЫЙ X25519** (важная поправка к прошлому выводу).
   Трассировка эмулятора показала в арифметике кривой лимбы Curve25519 и
   константу a24 = 121665 (`0xdb41`+`0x0001`), а также лимбы простого
   2^255-19. Константа не нашлась текстовым поиском, потому что реализация
   использует нестандартное представление больших чисел (16-битные лимбы в
   64-битных словах), но ВЫЧИСЛЯЕТ стандартный X25519. Значит X25519 в нашем
   `ModernCrypto` УЖЕ правильный.

5. **Симметричное ядро — blake2b-основанное, blake2b СТАНДАРТНЫЙ.** IV по
   адресу `0x23c090` байт-в-байт равен стандартному blake2b IV. Внутри
   шифра blake2b вызывается с `digest_size=24` (param-блок `18 00 01 01`,
   key_len=0, без salt/person) над входом `nonce(24) || key(64)` (захвачено:
   `blake2b_init` @0x82d258, `blake2b_update` @0x82db44 с conn+0x1b8 (24) и
   conn+0x1e8 (64), `blake2b_final` @0x82dd24).
   Salsa20/poly1305/chacha в `libg64.so` ОТСУТСТВУЮТ. Поэтому стандартный
   `crypto_box` (xsalsa20poly1305) сервер молча отвергает → «10101».

6. **DH-скаляр и shared подтверждены в памяти эмулятора.** Скаляр клиента
   (csk) лежит в conn+0x208 (вторая половина 64-байтного блока conn+0x1e8).
   `shared = X25519(csk, server_key)` — байт-в-байт совпал с
   `nacl.crypto_scalarmult(key[32:64], server_key)` в памяти эмулятора
   (@0x702ffb50). Это стандартный X25519. Поле conn+0x1e8 = [? (32) ||
   csk (32)].

7. **Открытый вопрос (где стена):** точная сборка симметричного AEAD
   (как shared → keystream+MAC). На синтетическом (неустановленном)
   соединении путь дешифровки ПОДТВЕРЖДЁННО идёт passthrough — out[16:]
   побайтово равен ct при любых ключах/nonce (проверено ct=00 vs ct=55:
   284/284 байт «расшифрованы» в самих себя). Значит keystream включается
   только на установленной сессии. Чтобы увидеть сборку, нужен путь seal
   первого сообщения (свежий DH, без установленной сессии) ИЛИ прогон
   полного хэндшейка — оба упираются в игровой object-graph (очередь
   сообщений/аккаунт/keypair), который не удаётся собрать статически на
   так сильно аутлайненном бинаре.

## Итог по шифру (что осталось)

Подтверждено и переиспользуемо в JS: X25519 (скаляр conn+0x208),
blake2b (стандартный IV, digest_size=24 над nonce||key), конверт
cpk||MAC16||ct, nonce-деривация. НЕ восстановлено: точная цепочка
shared → key → keystream → MAC (симметричная часть «box» на blake2b
вместо xsalsa20poly1305). Без наблюдения seal/established это
остаётся незакрытым чисто статически.

5. **Карта функций (arm64 RVA, libg64.so):**
   - `0x805f24` — приём/дешифр кадра (consumes conn+0x1b8 nonce24, conn+0x1e8
     key64, hardcoded server key); тело аутлайнено в `0x8300bc`.
   - `0x6acc98` (тело `0xbc12f0`) — симметричный AEAD-примитив сессии;
     `verify-first` (сначала проверяет MAC, потом отдаёт plaintext);
     keystate = conn+0x208; MAC-гейт = `0x6accf8 cbnz w0,…`.
   - `0x826ed8` — blake2b-компрессор/раунд.
   - `0x80e250` — диспетчер входящих; вызывает `0x805f24` на `ServerHello`.
   - ByteStream сообщения: объект в `msg+8`, данные `+0x38`, длина `+0x28`.

## Чего НЕ удалось (честно)

- **Извлечь байт-точный шифр логина чисто статически.** Эмулятор исполняет
  настоящий код, но:
  - дешифр-путь на синтетическом (неустановленном) соединении работает
    **passthrough** (pt == ct при любом ключе/nonce/keystate) — реальный
    keystream появляется только при валидном session-ключе из настоящего
    хэндшейк-KDF;
  - seal (шифрование, генерация MAC) — отдельная функция, которую не удалось
    изолировать так, чтобы гнать её «сырыми байтами» без игрового object-graph;
  - DH и KDF кастомные → нельзя подменить готовым X25519.

## Что это значит и варианты

Клиент готов на 95%: верный конверт, nonce, выбор ключа, структура тела.
Остаётся **одно** — ядро кастомного AEAD (keystream + MAC + кастомный DH).
Его можно получить только одним из:

- **A. Один референс-вектор keystream** от настоящего клиента (единоразовый
  дамп conn+0x208/keystream в рантайме) → детерминированная реализация на JS,
  проверяемая против эмулятора. Это и есть самый дешёвый «выход», но требует
  один раз снять рантайм-значение.
- **B. Прогнать весь хэндшейк+seal в эмуляторе end-to-end**, дав libg.so самой
  построить keypair/DH/KDF/seal при mock-I/O (сокет/JNI застабить). Больше
  апфронт-работы и неопределённости (Android/JNI-зависимости), но без рута и
  без устройства — чистый код в Termux.
- **C. Продолжать статический реверс** кастомного DH+AEAD до байт-точности
  (несколько сессий, сходимость не гарантирована на так сильно аутлайненном
  бинаре).

Инструменты для всех трёх путей лежат в скретчпаде сессии (эмулятор
`emulib.py`, драйверы, парсер pcap).
