# v70 login — как доискаться до рабочего `10101` без рута и без модификации APK

Коротко: сервер молча закрывает сокет на кадре `10101`. Крипта и длина тела
совпадают с живым дампом (см. `V70-STATUS.md`), поэтому вслепую перебирать
дальше бессмысленно — нужен **различимый сигнал от сервера** или **истинный
плейнтекст тела логина**. Ниже — два пути, оба без рута и без патча APK.

## Что уже зафиксировано анализом (не гадание)

- **Раскладка конверта — `native`, а не `hello`.** Живой дамп даёт плейнтекст
  287 Б (с токеном). Наш энкодер тела выдаёт ~261–271 Б. Это сходится только с
  `native` (накладные 26 Б → тело 261), а не с `hello` (накладные 49 Б →
  потребовалось бы тело 238). Значит прежний вывод про `native` верен —
  возвращать `hello` как дефолт неправильно.
- **Типы полей тела не трогались.** На v69 логин был `live-verified`; типы 34
  полей в v70 те же, изменились только **значения** 7 полей (field #6,
  dataReference, флаг +0x140, deviceModel +0x110, +0x120, seed +0x138,
  appStore +0x168). Любое из них может быть причиной.
- Крипто-параметры сервера 69→70 **не менялись** (тот же publicKey,
  keyVersion 60, protocolVersion 2, cryptoMode nulls-native19) — это бамп
  контента, а не смена протокола.

## Путь 1 — снять различимый сигнал с живого сервера (есть инструмент)

`tools/login-probe.js` гоняет настоящий хендшейк через боевой код (та же
крипта, те же энкодеры) и классифицирует реакцию сервера на `10101`:

| исход | что значит |
|---|---|
| `OK` | пришёл LoginOk — вход принят (кладём параметры в `config.json`) |
| `FAILED` | пришёл LoginFailed с кодом — тело **разобралось**, но отклонено по смыслу |
| `REPLY` | любой другой зашифрованный кадр после Login — конверт расшифровался |
| `SILENT` | сокет закрыт после Login без ответа — симптом v70 |
| `NOHELLO` | не было даже ServerHello — блок до стадии логина |
| `CONNFAIL` | не достучались до порта (нет сырого TCP — запускать там, где сервер виден) |

`FAILED`/`REPLY` — это **прогресс**: значит нашли раскладку/тело, которые
сервер хотя бы понимает, и дальше можно гнаться за кодом ошибки. `SILENT` на
всех вариантах — тело всё ещё не то.

Запуск (там, где виден игровой сервер — не из облачного контейнера):

```sh
# перебрать матрицу layout(native|hello) x body(native70|legacy69)
node tools/login-probe.js --sweep --account accounts/bot-1.json

# добавить кандидатов неизвестного +0x13c connection value
node tools/login-probe.js --sweep --conn 1448,0,1,70,877 --account accounts/bot-1.json

# один конкретный вариант
node tools/login-probe.js --layout native --body legacy69 --conn 0 --account accounts/bot-1.json

node tools/login-probe.js --sweep --json        # машиночитаемо
node tools/login-probe.js --verbose             # лог проводов из Messaging
```

Ключевое новшество: профиль тела `legacy69` — это **точные значения полей,
которые v69-клиент слал на live-verified логине** (только версия/fingerprint
всегда v70). Сочетание «правильная `native`-раскладка + проверенное v69-тело»
отдельно ещё не гоняли — начните с него:

```sh
node tools/login-probe.js --layout native --body legacy69 --account accounts/bot-1.json
```

Нашли `OK` — пропишите в `config.json`: `loginLayout`, `loginBodyProfile`
(`loginConnectionValue`, если перебирали `--conn`).

## Путь 2 — прочитать `Login::encode` из стокового `libg70.so` (read-only)

Это **не** модификация APK и **не** рут — просто чтение публичного файла.
Именно так уже получены RVA в комментариях (`0xf29d44` Login::encode,
`0xbbec20`, `0x1c7b04`). Их не хватает, потому что полного разбора тела в репо
нет (`.updates/v70/RE-*.md` в комплект не входят).

Что нужно: сам файл `lib/arm64-v8a/libg.so` (или
`libsupercell_brawlstars.so`) из стокового APK Nulls. Облачный контейнер его
скачать не может (егресс только HTTPS; APK ~1.3 ГБ и host закрыт политикой),
но на локальной машине это `unzip -p base.apk lib/arm64-v8a/libg.so > libg.so`.

Имея `.so`, дизассемблируем **окрестность 0xf29d44** (не весь бинарь) и читаем
порядок/значения полей:

```sh
pip install capstone
python3 - <<'PY'
import capstone, sys
data = open('libg.so','rb').read()
# ELF: найдите file-offset для RVA через заголовки программ; для грубого старта
# многие сборки мапят .text с virtual==file ниже первого PT_LOAD align.
rva = 0xf29d44
window = data[rva-0x40: rva+0x400]
md = capstone.Cs(capstone.CS_ARCH_ARM64, capstone.CS_MODE_LITTLE_ENDIAN)
for ins in md.disasm(window, rva-0x40):
    print(f'{ins.address:#x}  {ins.mnemonic}\t{ins.op_str}')
PY
```

Пришлите `libg.so` (или дизасм-окно вокруг `0xf29d44` и вызываемых оттуда
сеттеров) — и тело сверяется поле-в-поле с `Messaging/Messages/Client/LoginMessage.js`.

## Почему именно так

Отказ `10101` по проводу неразличим («не расшифровал» == «тело не понравилось»),
пока сервер не вернёт хоть какой-то кадр. Путь 1 ищет вариант, где он его
вернёт; путь 2 даёт истину из бинаря. Всё остальное (ещё один слепой перебор id
и комбинаций) уже исчерпано и сигнала не даёт.
