## Изменено в клиенте

- `Messaging/Messages/Client/LoginMessage.js` — значения приведены к нативным (RE-BODY §2):
  `+0x140` = `true`, `+0x110` = `""`, `+0x120` = Android ID, `+0x138` seed = 2, `+0x168` = 0.
  Все три поля переопределяемы через `config.loginFlagA / loginDeviceModel / loginAndroidId /
  loginClientSeed / loginAppStore`.
- `Crypto/ModernCrypto.js` — `config.loginLayout`:
  - `native` (по умолчанию) — `[VInt len(body)][body][clientNonce]`, как в libg70;
  - `hello` — прежняя v69-раскладка `[u8 len][ServerHello][clientNonce][body]`.
  Плюс публичный `ModernCrypto.writeVInt`.
- `config.json` — `loginLayout: "native"`.
- Тесты: `hello-wire` и `challenge-envelope` больше не прибиты к 69.252, добавлен кейс на обе раскладки.

## Живой дамп официального клиента (PCAPdroid, 24.11)

Снят с реального приложения: `ClientHello 776 B → ServerHello 32 B → Login 335 B → LoginOk 20104 (565 B, ver 1)`,
дальше обычные кадры `24101` (home data), `24399`, `20105` — все `ver 0`.
Разбор: `pcap_parse.js` (pcap → TCP → кадры Brawl), payload'ы в `*.hello.hex/.login.hex`.

Что это даёт:

- **Login = 335 Б = `pub32 ‖ tag16 ‖ 287`**, значит плейнтекст 287 = `VInt(261) ‖ body 261 ‖ nonce 24`.
  То есть раскладка `[VInt len][body][clientNonce]` подтверждена живыми байтами, а не только эмулятором.
- **Тело реального клиента — 261 Б**, наше — 306. Разница 45 Б: мы переполняем строковые поля
  (в частности `androidId` — у нас 36-символьный UUID вместо 16-символьного Android ID, и `openDeviceId`).
- `LoginOk` = `20104`, версия кадра **1** (не 0) — совпадает с `config.packetIds.loginOk`.
- Наш hello (777 Б) отличается от реального (776 Б) только длиной JSON-extra (timestamp).
- **Реплей захваченного Login сервер тоже закрывает** — тот же FIN через один RTT. Значит отказ нельзя
  списать на «сервер не смог расшифровать»: валидный конверт ведёт себя так же, оракула нет.

## Осталось (единственный блокер)

Сервер закрывает сокет на любом кадре `10101` — молча, без кода ошибки, ровно через один RTT.
Проверено и не помогло: все раскладки плейнтекста, все варианты значений тела (32 комбинации),
живой/пустой/отсутствующий токен, свежие id, оба хоста из dex, версии кадра 0…30,
нативные 76/72-байтные hello, повторные hello, задержки 0…1000 мс.

Байт-в-байт нативный конверт (снят эмулятором, воспроизведён в JS) сервер тоже закрывает —
оракула нет, отказ на расшифровке и отказ на содержимом неотличимы.

## Следующий шаг (не гадать, а снять с живого клиента)

Снять реальный кадр Login с работающего приложения — это единственный оставшийся источник истины:

1. Запустить Shizuku (сейчас `~/rish -c id` отвечает `Server is not running`) и
   `rish -c "tcpdump -i any -s0 -w /sdcard/v70.pcap host 135.125.37.166"`, затем зайти в игру.
2. Либо поставить на phone прокси-приложение (VPN-режим) и завернуть `:9339` в релей
   — в репозитории уже есть `tools/relay.js`.
3. Из pcap взять пару `ClientHello → ServerHello → Login` и сравнить с нашим конвертом
   побайтово (`probe_lib.js` умеет и то и другое).

Без этого шага дальнейший перебор — шум: 804 id, 32 комбинации тела и ~100 конвертов уже закрыты.

# Дамп 19:17 (создание аккаунта) — что дал и что починено

Файл: `PCAPdroid_24_нояб._19_17_08.pcap`, свежая установка + регистрация.

## Из дампа

```
10100 (776) → 20100 (32) → 10101 (315, ver 10) → 20104 (563, ver 1)
```

- Второй login на проводе — **315 Б** = `pub32 ‖ tag16 ‖ VInt(2) ‖ body 241 ‖ nonce 24`,
  то есть тело **241**, а не 261. Разница с прошлым дампом ровно **20 Б** = длина `passToken`
  (24 → 4 байта): на регистрации токена ещё нет. Всё остальное тело идентично по длине.
- `20100` = `00000018 <24 Б> ffffffff` — 32-байтный ServerHello, как в эмуляторе.
- Задержка `login → LoginOk` в дампе = **152 мс**; сервер закрывает наш кадр через те же ~150 мс,
  то есть отказ приходит на том же шаге, что и ответ.

## Что починено в клиенте (по этому дампу)

| Что | Было | Стало |
|---|---|---|
| hello JSON-extra | `high_memory` → 777 Б | `low_memory` → **776 Б**, побайтово как у живого клиента (кроме timestamp) |
| `deviceId` / `openDeviceId` | `crypto.randomUUID()` (36) | 32 hex без дефисов (как на проводе) |
| `androidId` | 36-символьный UUID | 16-hex `Settings.Secure.ANDROID_ID` |
| `+0x100` data ref | `(1,0)` — 2 байта | `(0,0)` — 1 байт (кэш пуст на логине) |
| `+0x138` seed | `apkSize ^ 4330295` (5 байт VInt) | `loginSeed` = 2 → 1 байт |
| поле #6 login | SHA1 из конфига | `invalid_files_content_update` (`loginContentFp`), SHA остаётся в hello |

Итог: тело ровно **261** (с токеном) / **241** (регистрация), конверт **335 / 315** — совпадает
с живым клиентом до байта по длине, включая версии кадров.

## Почему всё ещё закрывает

Сервер молча закрывает **любой** `10101`, включая побайтовый реплей настоящего конверта из дампа
(замерено: реплей, валидный-AEAD-мусор, битый тег, наш конверт — все ~150 мс, без кадра ошибки).
Значит по проводу отличить «не расшифровал» от «не понравилось тело» нельзя, а длина и раскладка
уже совпадают с настоящим клиентом — остаётся только **содержимое** зашифрованного тела.

Nonce бокса перепроверен: `blake2b24(PUB ‖ SERVER_PK)` — совпал с эмулятором точно
(`.updates/v70/audit/a1_nonce.py`, единственный матч из 160 кандидатов).

Дальше без плейнтекста — шум. Плейнтекст можно получить только с живого клиента (hook/frida/root),
патчить APK не просили.

  4 комбинации): **все закрываются**. Регистрация, которая проходила у реального клиента в дампе

  рантайм-конфига, не константа протокола; наше значение 1448 остаётся неподтверждённым,

  каталог модов (Visual Maxed и т.п.), к логину отношения не имеет.
- Три саб-агента (spk-truth, native-wire, oracle2), запущенные после рестарта сервера, не

## Про блокер `10101` — что можно и чего нельзя из этого окружения

Эмпирически доплыть до «входит» отсюда нельзя: контейнер не имеет сырого TCP-выхода на
`:9339` (егресс только через HTTPS-прокси), а Android/frida/root для снятия плейнтекста
живого клиента недоступны. То есть ни дифференциальный оракул по живому серверу, ни
снятие плейнтекста — два единственных оставшихся источника истины — здесь не
воспроизводятся. Перебор вслепую (id, комбинации тела, конверты) предыдущей итерацией уже
исчерпан и по проводу не даёт различимого сигнала.

Код же приведён к нативу настолько, насколько позволяет статический реверс: раскладка
плейнтекста и длины совпадают с живым дампом, крипта (box, nonce `blake2b192(pub‖spk)`)
совпадает с эмулятором. Закрыть блокер можно только сняв плейнтекст тела логина с рабочего
приложения (hook/frida/root) — дальше тело сверяется поле-в-поле с `LoginMessage.js`.
