# Выбор бойца в лобби: клиентские call-site'ы (libg.so)

Источник: `base.apk!/lib/arm64-v8a/libg.so`, md5 `c235f302de6c7fa28342422d85af5cc4` (совпадает с распакованным `$TMPDIR/libg.so`).
All адреса — RVA внутри libg.so (база файла 0). Сегменты: код `0x0..0x11a5410`, RW `0x11a9410..`, код `0x1315000..0x13434a4`.
Проверка формата: разбор vtables через `.rela.dyn` (`DT_RELA=0x9548`, `RELASZ=1599072`), границы функций через `.eh_frame_hdr` (`0x291e94`, 373 383 функций).

Статус пометок: **[П]** подтверждено дизассемблером, **[Г]** гипотеза/не подтверждено.

---

## 1. Механика отправки (подтверждено)

Идиома отправки клиент → сервер:

```
mov  w0, #<size>            ; 0x11a3840 = operator new
bl   #0x11a3840
mov  x0, xN                 ; ctor сообщения
bl   #<ctor>
adrp x8, #0x123d000
ldr  x8, [x8, #0x2a0]       ; глобал соединения 0x123d2a0
ldr  x0, [x8]               ; объект соединения
ldr  x8, [x0]               ; vtable соединения
mov  x1, <msg>
ldr  x8, [x8, #0x18]        ; slot 3
blr  x8
```

- **0x123d2a0 — глобал соединения** (сетевой send). [П]
- Второй, не относящийся к сети сендер: `0x13063c0` (210 xref, `ldr x1,[x1]` перед вызовом slot 0x18; хелпер `0x761c4c` без BL-вызовов). В сетевых путях ниже он не участвует. [П]
- Формат сообщений: vtable = 8 слотов. `[0]` dtor, `[1]` clone, **[2] encode, [3] decode, [4] version, [5] type getter (`mov w0,#id; ret`), [7] ctor**. [П]

### 3.1 Главный кандидат — 14352

`0xa64b24..0xa650b4` — диспетчер кликов по таблице кнопок: `0x89efb8(panel, id)` = `*(panel + 8 + (id-0x1f40)*8)`, т.е. id `0x1f40..0x1f63` — индексы 0..35 массива кнопок. Сравнение с нажатым виджетом, затем ветка `0x1f42`:

```
a64cf0  bl 0xd02b60 ; d03588     ; контекст игры
a64cf8  ldr x20,[x19,#0x128]
a64cfc  bl 0xd8efd8
a64d00  mov x1,x0 ; x0=x20
a64d08  bl 0xf338a4              ; map->get(key) -> объект с bool
a64d0c  ldrb w8,[x0] ; cbz w8    ; ЛОКАЛЬНАЯ ПРОВЕРКА (bool == 0 -> return)
a64d14  ldr x8,[x19,#0x138]      ; панель
a64d18  ldr x20,[x8,#0x150]      ; 8-байтовый id (hi,lo) / (class,index)
a64d1c  cbz x20 -> return
a64d20.. a64d30  new(0x98)
a64d3c  bl 0x54291c  -> w19 = [x20]      ; первый VInt
a64d50  bl 0x542924  -> w2  = [x20+4]    ; второй VInt
a64d60  bl 0xf3796c                      ; ctor 14352(w1,w2)
a64d64.. a64d74  conn=[0x123d2a0]; blr [vtable+0x18]   ; send
```

`0xc87a18` — та же последовательность байт-в-байт, значение берётся из `[screen+0x488]->+0x150`, перед этим `0xc879b4: bl 0xc86270` (поиск члена команды по 8-байтовому ключу через `0x542884`) и проверка bool.

**Что кладётся:** два VInt из одной 8-байтовой пары; порядок — `[+0]`, затем `[+4]`. [П]
**Что это значит:** либо `DataReference(class,index)` бойца, либо `LogicLong(hi,lo)` тега игрока. [Г] — не доказано; см. §6.
Слота (0..2) в 14352 **нет**. Флага «готов» в 14352 нет (он в 14355, bool).

### 3.2 14358 (три VInt) — единственный с явным анти-спам таймером

`0x8b164c`:
```
8b16d4  new(0xa0)
8b16e0  x8 = [this+0x2b0]; x0 = [x8+0x30]
8b16ec  bl 0x54291c  -> w19
8b1700  bl 0x542924  -> w2
8b1710  mov w3,#2                    ; ТРЕТИЙ VInt = 2 (константа)
8b1714  bl 0xf396e0                  ; ctor 14358
8b1730  blr [conn vtable+0x18]       ; send
8b1750  str w8(=1.0f), [x19,#0x7c]   ; кулдаун 1 с на объекте 0x123d2f8
```
Ветка входа проверяет `[x20+0x7c] > 0.0` и выходит. Т.е. это клиентский запрос с локальным троттлингом. [П]

### 3.3 14357 (список ссылок) — `0xa66bc8`
Строит `0xa8`-байтовый объект, добавляет в вектор `[this+0x130]` (8-байтовая пара) и `[this+0x288]->+8`, пишет count и хвостовой int, затем send. [П для кода, [Г] для смысла — похоже на «список выбранных» для мультивыбора.]

## 5. Чего клиент ждёт после выбора

- Все три пути (14352/14354/14358) отправляются «выстрелил и забыл»: локального optimistic-update в точке отправки не видно; сразу после `blr` идёт `b` в конец обработчика. [П]
- Состояние команды приходит в **24124** (v9): inner-структура 0x90 (`0xf33024`), в ней массив членов по 0x110 байт (`0xf37bf8` / decode `0xf37fa4`). У члена команды: `bool`, 8-байтовый id (`+0x8`, через vtable 0x128), **две DataReference `+0x10` и `+0x18`**, много VInt (0x20..0x50), вложенный объект 0x30 (`+0x58`), далее DataReference `+0x60, +0x68, +0x70, +0x78, +0x80, +0x88, +0x90, +0xa8, +0xb0`, массив DataRef `+0x98` (count `+0xa4`). [П]
- Кандидат на «выбранный боец» — одна из ссылок `+0x10`/`+0x18`/`+0x60`; какая именно — **не подтверждено**. [Г]
- 24125 (0x5e3d) — отдельный класс (v9), в разборе не участвовал; репозиторий трактует его как ответ на выход из лобби. [Г]

## 6. Что осталось непонятным (и следующий шаг)

1. **Семантика 8-байтовой пары в 14352/14358.** Репозиторий (`lib/Protocol.js:245`) считает 14352 = `team-kick` (два VInt = hi/lo тега). Дизассемблер одинаково допускает и `DataReference(class=16,index)`.
   *Следующий шаг:* в `0xa64b24` и `0xc8631c` проследить запись в `[screen+0x138]->+0x150` и `[screen+0x488]->+0x150` — кто и чем её заполняет (если там hero-id из brawler-меню — это выбор бойца; если accountId из списка участников — это кик).
2. **Какой id реально уходит при тапе по бойцу.** Попап `brawler_select` (строка `0x1b52db`, код `0xbf74dc`; элемент `brawler_selection_item` — ctor `0xa1a9a4`) сам пакет не строит: в диапазоне `0xbf4000..0xc00000` и `0xa0e000..0xa20000` нет ни одной записи vtable сообщения. Значит попап возвращает выбор наверх.
   *Следующий шаг:* найти callback попапа (параметр ctor `0xa1a9a4`, поля `+0x278` = brawler ref, `+0x284..0x287` = 4 bool) и вызывающую сторону в экране команды `0xa0f000..0xa18000`, затем — какой из `0xa63afc / 0xa64b24 / 0xa66ae4 / 0xa749a8` она дёргает.
3. **14354 = выбор или экипировка.** 8 полей (ref + int + 3 ref + 2 int + ref), отправляется из попапа (`0xbf22b4`, `0xbf2d80`) и из скинов. Не исключено, что именно 14354 несёт `HeroData`/скин.
   *Следующий шаг:* разобрать ctor-варианты `0xf35ccc` / `0xf35d2c` / `0xf35d80` — какие аргументы в `+0x90/+0xa0/+0xa8/+0xb0` и что за `DataRef` (класс объекта).
4. **14115 (0x3723)** — поля не разобраны (vtable `0x1227f30`). 14103/14113 в сборке отсутствуют.
5. **Подтверждение выбора** — нужен живой обмен: отправить 14352 с парой и посмотреть, изменится ли соответствующий DataRef у своего члена в следующем 24124.
