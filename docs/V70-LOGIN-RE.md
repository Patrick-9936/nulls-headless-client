# v70 login — реверс из `libg.so` (32-bit ARM, стоковый Nulls-клиент)

Снято статическим дизассемблером из `libg.so` (ELF32 ARM, stripped, build-id
`d33a92c8…`), сверено с живыми pcap-дампами. Это **истина по проводу**, а не
эмуляция. Весь разбор — read-only, без рута и без модификации APK.

## Карта (адреса — RVA, первый LOAD: RVA == file offset)

| узел | адрес | факт |
|---|---|---|
| строка `invalid_files_content_update` | `0x1502a6` | реальная строка в libg (подтверждает прежний `loginContentFp`) |
| ClientHello vtable | `0x11ce1b8` | `getMessageType` (vtable+0x14) → `0x2774` = 10100 |
| ClientHello `encode` | `0x962ec0` | 9 полей; большая строка-поле = key+license-блоб → это и есть 776-байтный hello |
| **LoginMessage vtable** | `0x11ea968` | `getMessageType` (vtable+0x14, `0x963174`) → **`0x2775` = 10101** |
| **LoginMessage `encode`** | **`0xe464e8`** | **34 поля** (ниже) |
| LoginMessage `decode` | `0xe46698` | slot[3] |
| ctor LoginMessage | `~0xe46330` | ставит vptr `0x11ea970` |

## Примитивы записи (ByteStream/ChecksumEncoder)

| writer | смысл | в терминах `DataStream/ByteStream.js` |
|---|---|---|
| `0x311ec8`→`0x2904fc` | LogicLong: пишет два элемента (hi, lo) через `vtable+0x28` | `writeVInt(hi); writeVInt(lo)` |
| `0x310614` (резерв 4 Б) | **Int32** (fixed big-endian) | `writeInt` |
| `0x310f1c` (резерв 5 Б) | **VInt** (Brawl zig-zag) | `writeVInt` |
| `0x30fdb4` | std::string (длина Int32 + байты) | `writeRequiredString` |
| `0x30ff84` | nullable-строка (null → длина `0xffffffff`) | `writeOptionalString` |
| `0x3103b4` | один байт | `writeBoolean` |
| `0xefd520` | nullable-ссылка (пусто → 0) | ~ `writeDataReference` / optional |
| `0x358ddc` | 64-бит через vtable (ещё один LogicLong) | `writeLong`/`writeVInt×2` |

> Длины строк в этом протоколе — **4-байтный Int32**, а не VInt: это видно прямо
> в plaintext-дампе ClientHello (`00 00 00 28` = длина 40 перед SHA1). Клиентский
> `writeRequiredString` (4-байтная длина) этому соответствует.

## Главный вывод (вероятная причина отказа)

1. **accountId** реальный клиент пишет как **LogicLong = `VInt(hi); VInt(lo)`**
   (поле 1). Текущий клиент пишет `writeInt(hi); writeInt(lo)` = **два Int32 по 4
   байта**. Если реальность — VInt, то первые же байты тела иной длины, и весь
   разбор на сервере рассыпается → молчаливый FIN. Это кандидат №1.
2. Далее порядок/типы в целом близки (token, major, const 1, build, optstr,
   optstr, dataref…), но в середине/хвосте расходятся: реальный encode имеет
   второй LogicLong (+0x114, поле 25) и иной набор строк/булей, тогда как текущий
   клиент в этих позициях шлёт `writeOptionalByteArray` и другой порядок пустых
   строк.

Длина тела в живом дампе (261 Б с токеном) совпадает с этой 34-полевой
раскладкой — структура та же, расходятся **типы отдельных полей и порядок хвоста**.

## Что из этого следует для фикса

Сервер молчит, пока тело не разберётся целиком. Значит цель — привести
`LoginMessage.encode` к **этому** порядку и типам байт-в-байт. Как только
структура сойдётся, сервер ответит (LoginOk либо LoginFailed с кодом — это уже
различимый сигнал). `tools/login-probe.js` ловит именно этот переход
`SILENT → REPLY/OK`.

Профиль `config.loginBodyProfile = "libwire"` (см. `LoginMessage.js`) — попытка
воспроизвести эту раскладку. Значения части хвостовых полей ещё уточняются по
функции-populate; структура (порядок + типы) взята из `encode` напрямую.

# Прогон probe 25.11 — тело исключено как причина

`login-probe.js --sweep` по account 0/280654299 против живого сервера:
**все 30 комбинаций** (layout native/hello × body libwire/native70/legacy69 ×
conn 0/1448/1/70/877) → **SILENT**. Важно: это `SILENT`, а не `NOHELLO`, то есть
`ServerHello` приходит, логин уходит, и сервер молча закрывает сокет.

Вывод, меняющий всё: **тело логина — не причина отказа.**

- Даже `libwire` — побайтовая раскладка из самого `Login::encode` — закрывается.
- Даже `hello` — крипто-раскладка, которой v69 проходил live-verified — закрывается.
- Значение `+0x13c` (connection) ни при каком из 5 кандидатов не помогает.

Раз корректная по структуре тело всё равно отбрасывается, блокер — на уровне
**крипто/конверта или проверки до тела** (ключ/nonce/лицензия/аккаунт), а не в
содержимом тела. Это разворачивает всю прежнюю работу (804 id, 32 комбинации
тела и т.д. били не по тому слою).

## Зацепка: серверный публичный ключ

`config.serverPublicKeyHex` (`656AA590…0E8656`, keyVersion 60) **в `libg.so`
отсутствует** — нет даже первых 8 байт. В нативной либе ключ не захардкожен: его
подаёт Java-слой/ассеты APK в рантайме через JNI. Значит проверить/взять
правильный ключ нужно из APK (assets или smali/dex, который настраивает нативную
крипту), а не из `libg.so`.

Кандидат №1 в причину: наш серверный ключ (или keyVersion) не тот, что ждёт v70-
сервер, — тогда box шифруется «не туда», сервер не может расшифровать и молча
роняет логин при любом теле. Это ровно тот симптом, что мы видим.

# НАЙДЕН НАСТОЯЩИЙ СЕРВЕРНЫЙ КЛЮЧ (classes.dex)

В `classes.dex` ровно один 32-байтный массив-литерал (второй — алфавит base64):
`7107a093895781d774710e621650d78312c0c58ea3097526f6a5c7130fc5c78f`.
Наш старый `config.serverPublicKeyHex` (`656AA590…`) не встречается ни в
`libg.so`, ни в `libwildcat.so`, ни в dex. 32-байтная константа в Java-слое — это
и есть пиннованный публичный ключ сервера (Curve25519), которым Nulls
переопределяет ключ Supercell. keyVersion остаётся 60 (так в живом ClientHello).

Это объясняет body-independent SILENT: с чужим ключом box шифруется «не туда»,
сервер не может расшифровать и молча роняет логин при любом теле/раскладке.
`config.json` → `serverPublicKeyHex` заменён на найденный ключ. После этого крипто-
слой должен разблокироваться, и тело/раскладка снова станут значимы — гонять
`login-probe.js --sweep`.

---

# Крипто-слой: где он НЕ находится (важно для следующего шага)

После того как тело исключено, искал сам login-box по бинарям:

- **`libg.so` (armeabi-v7a, что ты прислал) не содержит констант Salsa20/crypto_box**
  (`expand 32-byte k` и слова `0x61707865` отсутствуют во всём файле). При этом
  `Login::encode`/`ClientHello::encode` читаются чисто. Это значит, что крипто-ядро
  (box/nonce/ключ) в этом файле либо в упакованной/расшифровываемой-в-рантайме
  секции (Supercell пакует часть libg.so), либо его тут нет. Статически из этого
  файла ключ/шифр не достать.
- **`libwildcat.so`** содержит nacl + OpenSSL, но это frida-инжектор Nulls
  (`gum_interceptor_*`, `wildcat_js_get_signed_script`, ed25519/RSA-подписи) — его
  крипта обслуживает подписанные мод-скрипты и HTTPS к wildcat-api, не похоже, что
  это игровой login-box.
- `classes.dex` — host там есть, ключа нет (единственный 32-байтный массив = SHA-256).

Итог: точную крипту логина (серверный ключ, nonce, обёртку box) из присланных
файлов статически извлечь нельзя — ядро в arm32 `libg.so` недоступно (упаковано/
отсутствует). Прежние RVA в комментариях (`0xf29d44`, `0xbc0578`, `mov w0,#0x2775`)
— из **arm64** `libg.so`: там крипта, судя по всему, читается. Нужен
`lib/arm64-v8a/libg.so`.

# Реверс arm64 libg.so: крипта логина — НЕ стандартный crypto_box (ключевой вывод)

Снял с `lib/arm64-v8a/libg.so` (сборка подтверждена: RVA `0xbc0578` = `mov w0,#0x2775; ret`
= getMessageType логина). Что в либе есть и чего нет:

| примитив | статус в libg.so |
|---|---|
| Curve25519 scalarmult (DH) | **есть** — clamp `&0xf8 / &0x7f / \|0x40` в `0x6c3a44…0x6d5db8`, ladder `0x6d2204` |
| blake2b | **есть** (IV `08c9bcf367e6096a…` @ `0x23c090`) |
| SHA-256 / SHA-512 | есть (K-константы) |
| **Salsa20 / XSalsa20 / HSalsa20** (`expand 32-byte k`, `0x61707865`) | **НЕТ** нигде |
| **Poly1305** (clamp `0x0ffffffc`) | **НЕТ** |
| **ChaCha20 / AES** | **НЕТ** |
| строки крипто-классов (PepperCrypto/crypto_box/sodium…) | **НЕТ** (символы вырезаны) |

Вывод: конверт логина = **Curve25519 DH + своя (нестандартная) обвязка** —
кастомный KDF (похоже на blake2b), кастомный поток и кастомный 16-байтный MAC.
Это **НЕ** `crypto_box(xsalsa20poly1305)`, как предполагал прежний реверс
(RE-SEAL «HSalsa20» был из эмулятора, не из либы).

## Почему это объясняет ВСЁ

Наш `Crypto/ModernCrypto.js` реализует **стандартный tweetnacl box**
(xsalsa20poly1305). Реальная v70-крипта — **другой алгоритм**. При неверном
алгоритме сервер не может расшифровать конверт при **любом** ключе, теле,
nonce и раскладке → молчаливый `SILENT` на всех 30 комбинациях. Весь прежний
перебор (и мой `libwire`) бил не по тому слою — слой оказался крипто-алгоритмом.

## Честная граница

Чтобы это починить, нужно **полностью восстановить кастомную AEAD** (KDF→ключ,
поток, MAC, обработка nonce) из stripped aarch64 и найти серверный ключ
(он проходит через несколько слоёв вызовов, статически как константа рядом со
scalarmult не лежит — возможно подаётся из Java/рантайма). Это большой реверс,
и — главное — **без запуска клиента его результат нечем проверить**: любая
мелкая ошибка в кастомном шифре = тот же молчаливый отказ, неотличимый от других.
Это ровно та стена, в которую упёрся прежний реверсер («нужен плейнтекст живого
клиента»). Надёжный путь — рантайм-дамп (frida-хук на box-функцию), что требует
возможности исполнять код в процессе игры.

# Карта крипты логина (arm64) и единственный надёжный путь — frida-хук

Прослежен весь путь входа в arm64 `libg.so`:

| узел | адрес (RVA) | роль |
|---|---|---|
| send message | `0x805f24` | кадр + шифрование; спец-ветка для 0x2774/0x2775 (hello/login) |
| receive dispatch | `0x80de9c` | на ServerHello (0x4e84) → крипто-сетап → `0x805f24` (login) |
| ServerHello crypto setup | `0x805c8c` / `0x812194` | разбор 24-байтной сессии, деривация |
| ServerHelloMessage::decode | `0x8126b0` | читает сессию в поле +0x90 |
| **Curve25519 scalarmult** | `0x6d2204` | ladder; clamp `&0xf8/&0x7f/\|0x40` |
| blake2b | `0x82d258` | хэш (nonce/KDF) |
| Login getMessageType | `0xbc0578` | `mov w0,#0x2775; ret` |

Крипта абстрагирована через C++-объекты (vtable), поля состояния в RW-регионе
`0x1450xxx`, символы вырезаны, шифр кастомный. Серверный ключ грузится в состояние
соединения при инициализации (не лежит константой рядом с box).

## Почему статикой до рабочего фикса не дойти

Чтобы реимплементировать вход, нужно байт-в-байт воспроизвести кастомную AEAD
(KDF→ключ, поток, 16-байтный MAC, nonce) + достать серверный ключ. Любая мелкая
ошибка = тот же молчаливый `SILENT`, неотличимый от других, а оракула (живого
сервера) у меня нет. Это и есть стена: слепой реверс нестандартного шифра без
проверки практически не сходится.

## Надёжный путь: один frida-хук снимает ВСЁ за прогон

Если появится возможность исполнить код в процессе игры (`frida-server` на
рутованном тест-девайсе), хук на две функции закрывает вопрос целиком:

```js
// 1) scalarmult: аргументы раскрывают серверный публичный ключ и клиентский секрет
Interceptor.attach(Module.findBaseAddress('libg.so').add(0x6d2204), {
  onEnter(a){ this.out=a[0]; this.scalar=a[1]; this.point=a[2];
    console.log('scalar(csk)=', hexdump(this.scalar,{length:32}));
    console.log('point(server_pk)=', hexdump(this.point,{length:32})); }
});
// 2) send(0x805f24): снять плейнтекст логина и готовый конверт (cpk||tag||ct)
Interceptor.attach(Module.findBaseAddress('libg.so').add(0x805f24), {
  onEnter(a){ /* a[?] = буфер+длина сообщения до шифрования — снять дамп */ }
});
```

Снятые `server_pk`, `csk`, плейнтекст и шифртекст дают: ключ, схему KDF, поток и
MAC — после этого `Crypto/ModernCrypto.js` приводится к ним точно, а не вслепую.

# ПРОРЫВ: рабочий эмулятор libg.so исполняет настоящую крипту логина

Собран эмулятор на Unicorn (`scratchpad/re/emulib.py`): маппинг сегментов,
применение 69 242 релокаций (чтобы работали vtable-вызовы), заглушки libc,
map-on-fault. Он **реально исполняет** крипто-код libg.so.

Прогон `send(connection, loginMessage)` (0x805f24) уходит на 2460 вызовов вглубь,
доходит до blake2b (0x82d258). Динамически установлено:

- Крипта логина читает из состояния соединения: **conn+0x1b8 = 24 байта (nonce)**,
  **conn+0x1e8 = 64 байта (ключевой материал)**. Это рантайм-состояние, не
  константа либы (единственная rodata-константа в крипте — IV blake2b).
-差ференциальный тест (две раскладки ключа, один nonce): меняется 295 байт →
  это кастомная многораундовая blake2b-конструкция, а не простой поток+MAC.
- Подтверждено окончательно: конверт логина — **кастомная AEAD на blake2b**, не
  стандартный crypto_box. Поэтому наш `ModernCrypto.js` (tweetnacl box) — не тот
  алгоритм, и ни ключ, ни тело, ни раскладка не могли помочь.

## Что это даёт и что осталось

Эмулятор — это оракул: можно подавать контролируемые входы и читать выходы, то
есть крипту МОЖНО восстановить (в отличие от чистой статики). Осталось:
1. Собрать валидный объект loginMessage, чтобы encode дал настоящий body.
2. Снять преобразование plaintext→box по шагам (nonce-деривация, KDF, поток, MAC).
3. Либо реимплементировать в JS (blake2b уже есть в зависимостях), либо гонять
   крипту прямо через эмулятор как движок.
4. Отдельно: что кладёт ServerHello-обработка в conn+0x1b8/+0x1e8 (из 24-байтной
   сессии с провода и/или серверного ключа).

Это интрикатная, но теперь **выполнимая** работа — впервые есть исполняемый оракул.

# Шифр логина вскрыт (эмулятором): blake2b-поточный

Через эмулятор-оракул снято, как устроен seal (инлайн в send @ 0x8300bc):

- **KDF**: `derived = blake2b( nonce(24) ‖ key(64) )` — ровно эти 88 байт
  скармливаются в blake2b (hook 0x82dcb4 показал nonce‖key).
- **Поток**: blake2b-CTR блоками по 64 байта.
- **Шифрование**: XOR-цикл @ 0x8301bc: `ldrb w9,[pt]; ldrb w10,[ks]; eor; strb w9,[ct]; cmp #0x40`.
- Это **восстановимый на JS** шифр (blake2b уже есть в зависимостях).

Состояние крипты (conn+0x1b8 = nonce 24B, conn+0x1e8 = key 64B) задаётся при
обработке ServerHello. Осталось снять: формат блока keystream (что именно хешится
на блок), MAC (16 байт), и деривацию nonce/key из 24-байтной сессии ServerHello
+ клиентского ключа. Всё это теперь наблюдаемо через эмулятор.

Инструмент-оракул: scratchpad/emulator-deliverable (emulib.py).
